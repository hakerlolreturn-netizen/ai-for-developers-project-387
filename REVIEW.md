# Критерии ревью

Файл читает независимый ревьюер pull request (`.github/workflows/claude-review.yml`) и человек, который принимает решение о мерже. Ревьюер не писал этот код и не видит сессию реализации. Он ищет подтверждённые дефекты и проверяет, соответствует ли изменение спецификации.

## Источник задания

Спецификация и тикеты лежат в GitHub Issues, ссылки на них есть в описании PR (раздел «Связи»). Прочитайте обращение, спецификацию, тикеты и комментарий согласования. Каждый критерий приёмки из спецификации должен быть реализован. Расхождение со спецификацией считается дефектом, даже если код работает.

## Критерии календаря

Термины из `GLOSSARY.md`, решения из `docs/adr/`.

- Занятый слот не предлагается гостю и не бронируется повторно. Встреча, пересекающаяся с существующей, отклоняется, даже если запросы приходят подряд.
- Слот имеет длительность типа встречи, начинается на шаге стартов и целиком лежит в рабочих часах рабочего дня.
- Время хранится и показывается в часовом поясе владельца (ADR 0001).
- Страницы владельца работают без авторизации (ADR 0002), данные хранятся в памяти процесса (ADR 0003). Изменение не добавляет ни того, ни другого без нового ADR.
- Контракт API меняется только через `api/main.tsp` и `npm run gen` (ADR 0004). `api/dist/` руками не правится, бэкенд и фронтенд используют сгенерированные типы.
- Соседнее поведение сохраняется: запись гостя на свободный слот, список предстоящих встреч владельца и режимы, выбранные по умолчанию.
- Основной и негативный сценарии спецификации покрыты тестами. Тест проверяет видимое поведение (ответ API, отрисованную страницу), а не внутренние функции.

## Глубина проверки

Глубину выбирают по последствиям ошибки. Число изменённых строк риск не определяет.

| Изменение                       | Что проверять перед мержем                                      |
| ------------------------------- | --------------------------------------------------------------- |
| Подпись кнопки, текст           | Соответствие тексту задачи и отображение в интерфейсе           |
| Расчёт доступных слотов, запись | Основной сценарий, пересечения встреч и соседние случаи         |
| Отображение встреч владельцу    | Группировка и порядок, пустой список, режим по умолчанию        |
| Права и воркфлоу GitHub Actions | Изменение доступа к коду и секретам, отдельное решение человека |

## Формат замечания

Каждое замечание содержит:

- файл и строку;
- условия, при которых возникает ошибка (входные данные, состояние);
- последствие: что увидит или потеряет владелец или гость.

Пишите только подтверждённые дефекты, которые следуют из кода, спецификации или этого файла. Предположения без сценария ошибки не публикуются. Если подтверждённых дефектов нет, так и напишите в итоговом комментарии. Форматирование и стиль проверяет `npm run lint`, его вывод в ревью не повторяется.

## Повторное ревью

После нового push прочитайте прошлые замечания и ответы на них. Исправленные и отклонённые с объяснением замечания не повторяйте. Проверьте новые коммиты и поведение, которое они затрагивают.
